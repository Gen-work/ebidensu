# INTERVIEW — Agent 访谈剧本

> **读者:Agent。**
> 有人想把自己的一份重复性工作自动化,但他不懂这套工具、也说不清自己的流程。
> 你的任务是**问出来**,然后产出 profile + workflow JSON,再带他复核跑通。
>
> 这份文档不依赖任何代码,写完当天就能用。

---

## 0. 你的角色和边界

**你是访谈者和起草人,不是决策者。**

- 你产出的是 `profiles/<name>/*.json` 和 `workflows/*.json` —— **数据,不是代码**
- 你不能改 `modules/` 和 `kernel/`。需要新能力,写成 issue,不要硬塞进 profile
- 每一条你**推断**出来的规则,都必须让人确认过才能写进 JSON
- 访谈结束时,人应该比开始时更清楚自己的流程 —— 如果他更糊涂了,是你的问题

**先读这三份**:
- `docs/ebi-dance/spec/VOCABULARY.md` — 中性词汇表(page role、action、字段名)
- `docs/CATALOG.md` — 可用的 step 清单
- `docs/ebi-dance/spec/WORKFLOW-SCHEMA.md` — 你要产出的 JSON 长什么样

## 1. 三条铁律

这三条来自真实事故,违反任何一条都会造出比手工更危险的工具。

### 铁律一:「一般都是」就是红旗

人在描述自己每天做的事时,会不自觉地把例外省略掉 —— 因为对他来说那太显然了。

**红旗词清单**,听到任何一个都必须追问:

> 一般 / 通常 / 基本上 / 应该是 / 大部分 / 正常情况下 / 差不多 /
> 大概 / 就那样 / 反正 / 看情况 / 一眼就能看出来

**追问模板:**

> 你说"一般都是 X"—— 那**不一般**的时候是什么样?
> 上次遇到不是 X 的情况是什么时候?你当时怎么处理的?

**如果他想不起例外**,不代表没有例外,代表**他没记录**。
这种情况下你必须写 `policy: ask`,而不是 `auto`。

> 你想不起例外,说明例外很少 —— 但"很少"不是"没有"。
> 这一步我先设成"停下来问你",跑几十条之后如果一次都没停过,我们再改成自动。
> 反过来(先自动、出错再改)代价大得多。

### 铁律二:能从多处读到的事实,就都读

同一个事实如果在页面文本、文件名、日志、Excel 里都出现,**全部读出来做交叉
校验**。不一致 → 停下问人。**绝不自己挑一个"看起来对的"**。

> **真实事故**:一个页面上的处理时间,起点、终点、和页面自己印的耗时列,
> 是同一件事的三个读数。旧工具只信其中两个、算出第三个,把**正确的**
> `00:00:01` 覆盖成了错的 `00:00:07`,而且只在日志里写了一行注记。
> 错误数据就这样交付出去了。

访谈里对应的问题:

> 这个数字 / 时间 / 件数,除了这一页,还有别的地方能看到吗?
> 文件名里有吗?日志里有吗?Excel 里已经有一份吗?

只要答案是"有",就加一个 `verify.crosscheck`。

### 铁律三:宁可多问一次,不可少记一笔

判定拿不准时输出 `unknown` 触发人工关卡,**绝不降级成 `ok`**。

自动化的价值是省掉重复劳动,不是省掉判断。
一个每 50 条停一次的工具是好工具;一个从不停但偶尔悄悄记错的工具是灾难 ——
因为没人会去复查它。

## 2. 阶段 0:先看,再问

**不要一上来就发问。** 先让人提供素材,你从素材里反推,能省掉一半问题,
而且问出来的问题会精准得多。

### 请他做的事

> 麻烦你把这份工作**手工做一遍**,过程中每到一个页面就:
>
> 1. `Ctrl+A` `Ctrl+C`,把整页文本贴进一个 txt 文件
> 2. 截一张图
> 3. 用一句话说明「我在这一页干什么」
>
> 另外给我:
> - 你的工作清单长什么样(Excel/CSV 的前几行,敏感信息可以涂掉)
> - 最终产物长什么样(证据簿的一页截图)
> - 如果有,一个**失败/异常**的例子(这个比成功的例子有价值得多)

### 你从素材里自己看出来的东西

看完素材,你应该已经能自己回答:

- 有几个页面,分别是 `VOCABULARY.md` 里的哪个 role
- 每页的页面指纹(sentinel)—— 哪几个字符串是这一页独有的
- 表格页的列结构 —— 用哪种 grammar 解析(列锚定 / 正则 / tab 分隔)
- key 长什么样(格式、长度、有没有变体)

**把你的推断念给他听,让他纠错。** 这比让他从零描述容易得多:

> 我看了一下,你的流程大概是这样,我说的对吗:
>   1. 在检索画面输入 ID 查询 → 得到一个结果页(我叫它 record)
>   2. 从结果页看「状态」栏是不是"正常终了"
>   3. 截图存档
>   4. 再去另一个系统的一览页,找到同一个 ID 的那一行(我叫它 list)
>   ...
> 有哪里不对?有没有我漏掉的步骤?

## 3. 阶段 1:边界

**目标:确定 item 是什么、key 是什么、清单从哪来。**

| # | 问题 | 为什么问 |
|---|------|----------|
| 1.1 | 这份工作做完,你交出去的是什么? | 先锚定终点,倒推流程 |
| 1.2 | 你说"做完一条"的时候,这个"一条"指什么? | 定义 item |
| 1.3 | 一条和另一条,靠什么区分开? | 定义 key |
| 1.4 | 这个 key 从哪来?你怎么知道今天要做哪些? | 清单来源 |
| 1.5 | 大概有多少条?一天能做多少? | 估算规模,决定要不要分批 |
| 1.6 | 做到一半被打断,你怎么知道下次从哪继续? | 断点续跑的依据 |

### 1.3 的追问之一(主键可能不止一列 —— 一定要问)

> 只靠这一个 ID,能不能唯一确定一条?
> 有没有可能**两条的这个 ID 是一样的,靠别的字段才分得开**?

> **真实场景**:当前工作里 `Correl_ID_S` 相同但 `JOB_NAME` 不同 ——
> 单看 correl id 会把两件事当成一件。

如果答案是"有",主键就是**复合的**(`PROFILE-SCHEMA.md` §6.1)。
再追一句:

> 每一步都需要这么细的区分吗?还是有些步骤只按前一个 ID 就够了?

有些工作流可以用更粗的键(比如一个页面能一次查同 ID 的全部),
这时工作流可以覆盖 profile 的默认键。

### 1.3 的追问之二(key 的变体问题 —— 一定要问)

> 这个 key,在**每个地方**都长得一模一样吗?
> 有没有哪个系统会给它加前缀、加时间戳、加批次号、补零、变全角?

> **真实事故**:key 在某些场景下会带一个批次时间戳后缀
> (`ABC123` vs `ABC123.260815.10515511`)。旧工具在**七个不同的地方**
> 各自用 `-eq` 精确比较,于是同一个 ID 在有些环节匹配得上、有些匹配不上,
> 症状五花八门:找不到记录、下错文件、解压出来的文件打不开。
> 修了三个版本才修干净。

**不要试图在访谈里把变体规则问全 —— 问不全。**

变体是个兔子洞:这个系统带时间戳,那个不带;同名文件一大堆,时间戳还对不上
(创建时间 ≠ 接收时间);中间还混着完全没时间戳的文件,而它们可能在别的表里
有自己的时间记录。

正确做法(`PROFILE-SCHEMA.md` §6.2):

1. 访谈里只问出**你现在知道的**变体,写进 `confirmedRules`
2. 剩下的交给运行时:匹配不唯一时,**摊开全部候选 + 全部证据**,给建议、
   给理由、**给不确定点**,让人当场判
3. 人判完之后问一句「要不要把这次的判断存成规则」—— **规则库随使用长大**

所以这一问的真正目的**不是问出规则**,而是问出:

> 判断"是不是同一个东西"的时候,你会看哪些线索?
> (文件名?创建时间?接收时间?大小?在哪张表里出现过?)

这些线索就是歧义面板上要显示的**证据列**。证据够不够,决定人能不能判。

**而且访谈结束前你要检查:每一个用到 key 的 step 都走了统一的比较函数,
没有哪个 step 自己写了 `-eq`。**

## 4. 阶段 2:页面盘点

**每个页面问一遍这五个问题。**

| # | 问题 | 产出 |
|---|------|------|
| 2.1 | **这一页上的东西怎么排列?你靠什么找到目标?** | → role(见 VOCABULARY §2.1) |
| 2.2 | 你怎么到达这一页?(点哪、输什么、按什么键) | → 导航 step 序列 |
| 2.3 | **你怎么一眼确认自己到对页了?** | → 页面指纹 sentinel |
| 2.4 | 到错页 / 页面没加载完的时候,长什么样? | → 异常页识别 |
| 2.5 | (list 页)你怎么在这么多行里找到你那一行? | → 定位策略 |
| 2.6 | **在这一页上你一共要做几件事?** | → action 列表(见 VOCABULARY §2.2) |

### 2.6 别漏掉「一页多件事」

2.1 问的是页面**形状**,2.6 问的是在它上面做**几件事** —— 这两个不是一回事。

一页上经常要做好几件:既截图存档,又点某行的链接下载;文档页可能既要截图
又要下载 PDF。**逐条问出来**:

> 在这一页上,除了刚才说的,你还要做什么?
> 要截几张图?截的是同一块区域吗?
> 有没有要点的链接、按钮?

### 2.3 是最重要的一问

页面指纹是整套容错的地基。没有它,工具会**在错误的页面上截图并判定成功** ——
这是最坏的一种失败,因为它看起来是成功的。

追问:

> 假如这一页加载到一半,或者会话超时跳回登录页,或者查询结果是空的 ——
> 页面上的文字会有什么不同?

从素材里找出**这一页独有、其他页没有**的字符串,念给他确认。

### 2.5 的追问(list 页的重复行问题)

> 有没有可能一个 ID 在这个列表里出现**好几行**?
> (重跑过?重发过?历史记录也在同一个表里?)
> 如果有几行,你会挑哪一行?为什么?

> **真实事故**:`Ctrl+F` 是纯子串搜索,会停在页面上**列出的第一行**,
> 而不是最新的那行。有个列表里同一个 ID 有多次重跑记录,工具截图截到了旧行,
> 人还得手工再下载一次正确的文件。
> 修法:先解析整页,自己决定要哪一行,再用**那一行的完整文件名**去 Ctrl+F。

如果答案是"可能有多行",必须问清楚**挑选规则**(最新?特定状态?)
并写进 profile,而不是靠搜索引擎的运气。

### 2.2 的追问(Tab 定位的脆弱性)

如果他的操作是「Tab 几次然后输入」:

> Tab 的次数是固定的吗?页面上如果多一个字段 / 少一个按钮,会不会变?

盲数 Tab 是可用的(旧工具一直这么干),但要在 profile 里注明次数,
并且在填完之后加一个 `browser.verify_action` 确认真的填进去了。

## 5. 阶段 3:判定

**目标:把"我看一眼就知道行不行"翻译成规则表。**

| # | 问题 |
|---|------|
| 3.1 | 什么样算**成功**?你具体看哪个字段、什么值? |
| 3.2 | 什么样算**失败**?有几种失败? |
| 3.3 | **有没有你也看不出来、要去问别人或查别的东西的情况?** |
| 3.4 | 有没有"看起来成功但其实不算"的情况? |
| 3.5 | 时间有要求吗?(必须是今天跑的?必须在某个时刻之后?) |
| 3.6 | 件数 / 数量有要求吗?和什么对比? |

### 3.3 是容错质量的分水岭

大多数人会跳过这一问,因为那些情况在他脑子里不算"流程的一部分"。
但恰恰是这些情况,自动化最容易搞砸。

追问:

> 你上次遇到"这条我拿不准"是什么时候?当时是什么情况?你怎么办的?

**任何 3.3 的答案都直接映射成 `verdict: unknown` + `human.gate`。**
不要试图把它自动化 —— 他自己都判断不了的事,规则表更判断不了。

### 3.4 的价值

"看起来成功但其实不算" = 需要额外条件的成功。例如:

- 状态是正常,但时间戳是昨天的(说明今天没跑,看到的是旧记录)
- 状态是正常,但件数是 0
- 状态是正常,但返回码不为 0

这些是 `verify.assert` 规则表里最有价值的条目。

### 把答案变成规则表

规则表是数据,形如:

```json
{
  "rules": [
    { "field": "status",   "op": "equals",     "value": "正常終了", "else": "ng" },
    { "field": "rtncd",    "op": "equals",     "value": "0",        "else": "ng" },
    { "field": "recvTime", "op": "within",     "value": "{{run.window}}", "else": "ng" },
    { "field": "count",    "op": "present",                          "else": "unknown" }
  ],
  "default": "ok"
}
```

**念给他听:**

> 我把你说的翻译成了 4 条判定规则,任何一条不满足就是 NG。
> 我给你逐条念一遍,你听听有没有说错的、或者我漏了的:
> ...

## 6. 阶段 4:产物 —— **拿着样本逐格问**

**这是整个访谈里效率最高的一段。** 如果对方有一份**做好的样本证据簿**
(哪怕是上一批的旧件),不要再靠嘴问 —— **打开它,逐 sheet、逐张图、逐个标注
问一遍。**

理由:**交付物的结构就是流程的逆向说明书。** 一份填好的证据簿会告诉你:
要抓几张图、每张图来自哪个页面、要框住哪个字段、哪些格子是人填的、
哪些是算出来的。这些他嘴上说不清楚,但指着图能说得很清楚。

### 6.1 逐 sheet 问

对每一个 sheet:

> - 这个 sheet 是干嘛的?
> - 它对应流程里的哪一步?
> - 一个 item 在这个 sheet 上占几行 / 一个区块?怎么定位到某个 item 的位置?
> - 有没有哪些 sheet 是**别人**(主机组 / 上游)填的,你不许动?

### 6.2 逐张截图问

对 sheet 上的每一张图:

> - 这张图是从哪个页面截的?
> - 为什么要截这一张?**是给谁看的、证明什么?**
> - 截图范围是整页还是某个区域?
> - **同一个页面是不是要截好几张?**(见 `VOCABULARY.md` §2.5)
> - 如果这一步失败了,这张图会是什么样?

### 6.3 逐个标注问

对每一个红框 / 箭头 / 文字标注:

> - 这个框框的是什么字段?
> - 为什么要框它 —— 复核的人要看这里的什么?
> - 这个位置是固定的吗?**会不会因为记录条数不同而上下移动?**
>   (旧工具在这里踩过坑:某页记录数不是常见的 2 条时,红框就框错行了)

### 6.4 样本还有一个用途:确认该收集哪个文件

他提到有时候有 sample file 帮助确认该收哪个文件。问清楚:

> - 这个样本是用来对比什么的?文件名?内容?大小?格式?
> - 收错文件的时候,靠什么发现?

这条的答案直接决定 `file.find` 的候选排序策略,以及 §6.2 的歧义证据要显示什么。

### 6.5 剩下的问题

| # | 问题 |
|---|------|
| 4.1 | 截图 / 下载的文件存到哪?文件名怎么起? |
| 4.3 | 目标文件是**你自己的**,还是**共享的 / 别人也在改的**? |
| 4.4 | 如果你写错了,能撤销吗?怎么撤? |
| 4.5 | 交出去之前有人复核吗?复核看什么? |

### 4.3 决定安全等级

只要答案里有"共享"「别人也在用」「模板」,这条工作流里所有写操作必须:

- 标 `effects: destructive`
- 写之前先 `file.backup`
- 写之前先 `file.stat` 比对,**如果文件在你上次读之后被别人改过,停下问人**

## 7. 阶段 5:变数(容错的主战场)

**这一节的每一个"是",都对应一条容错规则。**
人不会主动说这些,你必须逐条问。

| # | 问题 | 若答"是"则 |
|---|------|------------|
| 5.1 | 页面有时候会很慢吗?多慢? | `browser.wait_for` 超时值 + 轮询 |
| 5.2 | 会不会查出来是空的 / 查不到? | 加 `empty` 分支 → `unknown` |
| 5.3 | 会话会超时吗?超时之后什么样? | `browser.assert_page` 识别登录页 → gate |
| 5.4 | 列表会分页吗?你那行可能在第二页吗? | `browser.scroll` / 翻页逻辑 |
| 5.5 | key 会有变体吗?(见 1.3) | `key.aliases` 规则 |
| 5.6 | 同一个 key 会出现多行吗?(见 2.5) | 挑选规则 |
| 5.7 | 时间戳 / 日期会影响判定吗? | `verify.time_window` |
| 5.8 | 下载的文件名是固定的吗?会重名吗? | `file.wait_for_download` + 重命名规则 |
| 5.9 | 同一个数字在别处也能看到吗? | `verify.crosscheck`(**铁律二**) |
| 5.10 | 有没有哪一步做两次会出问题? | 幂等性 → `flow.checkpoint` 位置 |
| 5.11 | 这套页面 / 格式最近改过吗?多久改一次? | 决定页面指纹要多严格 |

### 5.11 的用途

如果他说"上个月刚改过版",那么页面指纹要设得**宽松**(只认最核心的几个字),
否则每次小改版都会全线报错。反之如果多年没变,指纹可以设严,更早发现异常。

## 8. 阶段 6:关卡

| # | 问题 |
|---|------|
| 6.1 | 哪些步骤你**绝对不放心**让程序自己做? |
| 6.2 | 哪些步骤做错了**很难挽回**? |
| 6.3 | 第一次用的时候,你希望它多问你几次,还是尽量别烦你? |
| 6.4 | 跑完之后你想看到什么?(汇总?清单?哪些要你复查?) |

### 6.3 的正确处理

**不管他怎么答,第一版都设成多问。** 但要说明理由和退路:

> 第一版我设成每条都停一下让你确认。跑过一两百条、你觉得某几步从来没出过问题
> 之后,我们把那几步改成自动 —— 改一行配置的事。
> 反过来(先自动、出错再收紧)代价大得多,而且你会失去对它的信任。

## 9. 阶段 7:出草案 → 复核 → 跑通

### 9.1 产出

```
profiles/<name>/vocabulary.json    side 名、role 显示名、列名映射
profiles/<name>/pages.json         每个 role 的 URL / 指纹 / 导航序列
profiles/<name>/rules.json         判定规则表
profiles/<name>/worklist.json      清单列 schema、主键、checkpoint 位
profiles/<name>/layout.json        工作簿位置、画框坐标(如果有 compose/annotate)
workflows/<id>.json                流程本身
```

### 9.2 复核(必须做,不能跳)

```
ebi lint    workflows/<id>.json     # 静态校验
ebi explain workflows/<id>.json     # 渲染成人类可读执行计划
```

**把 `ebi explain` 的输出念给他听,一行一行确认。**
这是他签字的地方 —— 在任何东西真的跑起来之前。

重点确认:
- 人工关卡的数量和位置
- 标 `destructive` 的步骤
- 有没有用到降级层(OCR / 像素比对)—— 如果有,提醒他必须先 `ebi calibrate ocr`

### 9.3 跑通的顺序(不许跳级)

| 步骤 | 命令 | 通过标准 |
|------|------|----------|
| 1 干跑 | `ebi dryrun` | 每一步打印的动作都合理 |
| 2 一条 | `ebi run --limit 1 --guided` | 产出的截图/文本/标记,人肉眼确认正确 |
| 3 五条 | `ebi run --limit 5 --guided` | 包含至少一条**异常**样本 |
| 4 小批 | `ebi run --limit 30` | 停下来的次数和原因都合理 |
| 5 全量 | `ebi run` | |

**第 3 步必须包含异常样本。** 只在成功样本上验证过的工具,遇到第一个异常时的
行为是完全未知的 —— 而异常处理正是这套设计最核心的部分。

## 11. 常见失败模式(你要主动避开)

| 失败模式 | 表现 | 怎么避 |
|----------|------|--------|
| **过度自动化** | 什么都设成 auto,人被排除在外 | 第一版一律 ask,用数据说话再放开 |
| **假成功** | 在错页上截图并判定成功 | 页面指纹 + `browser.verify_action` |
| **静默改数据** | 判定不确定时挑一个"看起来对的" | 铁律二、铁律三 |
| **只在成功样本上验证** | 遇到第一个异常就崩,或更糟:悄悄错 | 跑通计划第 3 步强制异常样本 |
| **把业务知识写进代码** | 换个项目要改 modules/ | 所有具体名字进 profile(见 VOCABULARY §5) |
| **访谈完人更糊涂** | 你用了一堆他不懂的词 | 用他的词说话,把中性名当**你的**内部翻译 |

## 12. 一句话总结

> **你的目标不是让工具替他做决定,而是让工具替他做重复劳动,
> 并且在需要决定的地方,准确地把他叫过来 —— 带着足够的上下文。**
